## 1. 범위

현행 시스템 전체를 옮기지 않는다. **관계형 DB를 다루는 방식(SQL 매핑·트랜잭션·페이징·인덱스)을 표준 스택에서 검증할 수 있는 흐름 3개**만 옮긴다.

| 구분 | 대상 | 근거 |
|---|---|---|
| 이관 | 상품 목록·검색(AS-F-020) | 페이징을 DB로 옮기는 대표 흐름(C-04) |
| 이관 | 주문 확정(AS-F-040~042) | 여러 쓰기를 한 트랜잭션으로 묶는 대표 흐름(C-03, C-11-3) |
| 이관 | 주문 내역 조회(AS-F-044) | 회원별 대량 데이터 조회와 인덱스 실측 대상(C-04) |
| 이관(선행 조건) | 로그인·세션(AS-F-002) | 주문 흐름의 전제. 최소 범위만 구현 |
| 신규 | DB 스키마 Oracle 이관, 대량 시험 데이터 생성, 실행계획 측정 | 측정 단계(이관 후)의 입력 |
| **제외** | 회원가입·수정·탈퇴, 건강 기록(AS-F-010~013), 상품 관리(AS-F-022~025), 장바구니(AS-F-030~034), 리뷰, 게시판, 추천 콘텐츠, 화면(JSP) 이관, 다국어, 클라우드 배포 | 5절 「채택하지 않은 안」 참조. 현행 시스템은 그대로 보존해 전후 비교에 쓴다 |

## 2. 기능 요구사항

우선순위: H = 이관의 목적과 직결, M = H를 쓰려면 필요, L = 있으면 좋으나 빠져도 목적 달성.

| ID | 요구사항명 | 설명 | 근거 | 우선순위 |
|---|---|---|---|---|
| RQ-F-001 | 스키마 이관 | `member`·`product`·`orders`·`order_items`를 Oracle DDL로 옮긴다. 자동 증가는 IDENTITY, `TEXT`는 `CLOB`, `DATETIME`은 `TIMESTAMP`로 바꾸고 FK·CASCADE 규칙을 현행과 같게 유지한다 | 01 §3 | H |
| RQ-F-002 | 상품 목록 페이징 | 상품 목록을 페이지 번호·크기로 조회한다. 페이징은 SQL(`OFFSET … FETCH NEXT`)에서 처리하고 전체 건수를 함께 돌려준다 | AS-F-020, C-04 | H |
| RQ-F-003 | 상품 검색 | 상품명·제조사 중 선택한 항목과 검색어로 목록을 거른다. 검색 항목은 허용 목록에서만 고르고, 검색어는 바인드 변수로 전달한다(동적 SQL) | AS-F-020, AS-F-060, C-06 | M |
| RQ-F-004 | 로그인 | ID·비밀번호로 로그인하면 세션을 만든다. 비밀번호는 단방향 해시로 저장·비교한다 | AS-F-002, C-07 | M |
| RQ-F-005 | 인증 확인 | 주문 관련 요청은 서버에서 로그인 여부를 확인하고, 미로그인이면 401로 거절한다. 검사는 화면별 코드가 아니라 공통 인터셉터 한 곳에서 한다 | C-05 | M |
| RQ-F-006 | 주문 확정 | 로그인 회원이 상품 ID·수량 목록과 배송 정보(받는 사람·배송일·주소·우편번호)를 보내면 주문을 만든다. 가격은 요청값이 아니라 DB의 현재 할인가로 계산한다 | AS-F-040~042, C-13 | H |
| RQ-F-007 | 주문 원자성 | 주문 헤더와 주문 상품 저장을 **한 트랜잭션**으로 처리한다. 어느 한 쪽이 실패하면 둘 다 반영하지 않고 오류를 돌려준다 | C-03, C-10 | H |
| RQ-F-008 | 주문 입력 검증 | 상품 목록이 비었거나, 수량이 1 미만이거나, 존재하지 않는 상품이 있으면 주문을 만들지 않고 400으로 거절한다 | C-08, C-11-3 | H |
| RQ-F-009 | 주문 내역 조회 | 로그인 회원 본인의 주문을 최신순으로 페이징해 조회한다. 주문 상품은 주문 목록과 함께 한 번의 조회 흐름으로 가져온다(주문 수만큼 반복 조회하지 않는다) | AS-F-044, C-04 | H |
| RQ-F-010 | 본인 데이터 한정 | 주문 내역은 세션 회원의 주문만 돌려준다. 다른 회원의 주문 ID를 넣어도 조회되지 않는다 | C-05 | H |
| RQ-F-011 | 시험 데이터 생성 | 회원·상품·주문·주문상품의 대량 시험 데이터를 재현 가능한 스크립트(고정 시드)로 만든다. 주문은 50만 건 이상 | 신규(측정 입력) | M |

## 5. 채택하지 않은 안과 사유

| 안 | 채택하지 않은 이유 |
|---|---|
| JPA(Hibernate) | SQL이 프레임워크 뒤로 숨는다. 이 이관의 목적은 SQL·인덱스·실행계획을 직접 다루고 측정하는 것이라 SQL을 그대로 드러내는 MyBatis를 택했다. 공공·금융 SI의 MyBatis 사용 관행도 고려했다 |
| 현행 전 기능 이관 | 대부분의 화면은 같은 CRUD 패턴의 반복이라 기능을 늘려도 검증하려는 것(트랜잭션·페이징·인덱스)이 늘지 않는다. 기간(K-05) 안에서 측정 단계를 지키는 쪽을 택했다 |
| MySQL 유지 | 현행과 같은 DB면 이관 시 생기는 타입·페이징·시퀀스 차이를 다룰 일이 없다. 공공·금융 현장에서 쓰는 Oracle로 옮겨 그 차이를 직접 처리한다 |
| 화면(JSP·Thymeleaf) 이관 | 화면은 이번 검증 대상이 아니다. REST API로 노출하고 테스트·측정은 API와 SQL 수준에서 한다 |
| Spring Security 전면 도입 | 필요한 것은 "주문 요청의 서버 측 로그인 확인"과 "비밀번호 해시"다. 인터셉터 1개와 해시 라이브러리로 충분해 의존성을 늘리지 않았다 |
| 장바구니 DB 저장 | 주문 확정 요청이 상품·수량 목록을 직접 받으면 장바구니 없이도 트랜잭션 흐름을 검증할 수 있다. 가격은 서버가 DB에서 다시 읽는다(RQ-F-006) |
| 성능 목표값 사전 설정 (예: "p95 500ms 이하") | 로컬 무료 에디션에서 처음 재는 값이라 근거 있는 목표를 세울 수 없다. 목표를 먼저 정하면 측정을 그 숫자에 맞추게 된다. 대신 전후 비교와 측정 조건 기록을 요구사항으로 삼았다(RQ-N-005~007) |
| 건강 기록 이관 | 트랜잭션 예시로 쓸 수 있으나 주문 확정과 검증 내용이 겹친다. 날짜 단위 집계(C-13)는 요구 정의부터 다시 해야 해서 이번 범위에서 뺐다 |
| 클라우드(EC2) 배포 | 비용 원칙(K-03) |
